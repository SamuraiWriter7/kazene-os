## Overview

Kazene Windmill Network v1.0.0 establishes a testable control specification for a circulation-based, modular AI defense architecture. Kazene acts as a logical policy axis; detachable and replaceable blades provide specialized observation and analysis without granting untrusted agents authority over safety controls.

**Core design principle:** Do not modify or retaliate against the external attack entity. Instead, bound its effects using independent safety controls and circulate only isolated, validated observation records.

## Included in v1.0.0

- **D (Forward):** bounded forward observation and Trace capture.
- **R (Reverse):** offline provenance traversal of stored Trace without contacting the suspected source.
- **N (Neutral):** disengagement from new untrusted interactions while preserving records.
- **P (Park):** shut down observation workers while maintaining independent boundary protection.
- **Dual-channel model:** separate D/R processing with a shared resource budget and safety override.
- **Replaceable blades:** independently validated role, authority, swap fencing, trace integrity, and post-replacement health.
- **Safety precedence:** core failure and critical pressure override operational modes; authorization or evidence inconsistencies trigger neutral state.
- **Provenance and limitations:** reverse traversal yields hypotheses, not proof of attacker identity.

## Validation boundary

This release is a **specification and synthetic validation milestone**. It does not establish that live GPTs cooperate autonomously, that real malicious traffic is isolated, that signatures are cryptographically verified, that simultaneous failures are resilient, or that real-world attack attribution works. Resource and pressure thresholds in the examples are toy values. Deployment requires independently verified ingress protection, authorization, concurrency, logging integrity, and adversarial testing.

## Version policy

Version `v1.0.0` freezes the documented conceptual interfaces and synthetic conformance cases. Future changes should be proposed with explicit versioned fixtures and a changelog. This record is not, by itself, a GitHub Release or a Git tag.
